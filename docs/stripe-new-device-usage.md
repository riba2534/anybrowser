# 用「新设备」登录另一个 Stripe / Link 账号

Stripe 和 Link 判断一台设备，不只看浏览器 Profile：它们同时看站点 Cookie、Stripe 服务端签发并锚定的 `m`、本地存储和出口 IP。只换其中一两样，网站仍可能把两个账号归到同一台设备。

本文只讲怎么操作和怎么查，原理与证据见 [实施方案](stripe-new-device-plan.md) 与 [证据目录](stripe-new-device-evidence/)。

## 什么算一台新设备

以下五项同时成立才算，缺一不可：

1. **新 Profile**：新的 Profile 目录，不与旧身份共用同一份浏览器资料。
2. **新种子**：整套指纹重新生成，种子、屏幕、字体、CPU、内存一起换。
3. **新设备标识**：应用生成新的 36 位小写 UUIDv4，首访前写进启动网址的 `__stripe_mid`。
4. **空 cookie jar**：旧站点数据已经清掉，包括旧账号留下的 Cookie 与本地存储；首访前只由应用写入本 Profile 自己的标识。
5. **独立出口 IP**：这个 Profile 有自己的代理，出口地址与其他 Profile 不同，最好还在不同地区或不同运营商。

只有新种子、只有新 Cookie、只有新屏幕，都不够。

## 正确操作

1. 点「新建 Profile」，或者打开已有 Profile 点「整套重新生成」。
   - 「整套重新生成」会先换上整套新身份。新 Profile 直接保存并启动即可。
   - 旧 Profile 有旧数据：停止状态下保存后立即清除，运行中则在重启时清除。清除完成之前不要当新设备用。
   - 「复制为新 Profile」也可以：它会给副本换种子和新设备标识，但资料目录是新建的、不共用旧数据。
2. 在「启动选项」里填**实际的登录域名**，例如 `https://app.link.com` 或商家的结账域名。
   - 设备标识只种到启动网址的主机，最多 20 个；之后从别的域名进入不会自动补种。
   - 不填启动网址则没有种子，Stripe 首报里的 `b.d`/`b.e` 会是 `NA`，要等页面自己拿到服务端签发的新值。
3. 在「代理」卡片填写这个 Profile 专用的代理，点「检测」确认出口与预期一致，再点「按出口 IP 填写时区和语言」。语言、时区要跟着出口走，不要留成这台 Mac 的设置。
4. 看指纹卡片的一致性提示，把红色项处理掉。重点有：
   - `exit-shared`：和别的 Profile 共用出口，需要换代理；
   - `screen-host-shared`：没有屏幕配置；生成的身份都带屏幕，只有手工清空才会出现；
   - `font-profile-platform`、`font-spoof-disabled`：字体表与平台不符，或字体改写没开；
   - 品牌版本高于内核、平台版本不匹配等常见项。
5. 关闭「恢复上次会话」再启动。恢复的旧标签可能早于设备 Cookie 写入。
6. 用「保存并启动」正常打开窗口，先在带窗口的模式下完成首访，登录新账号。
   - 登录时另开一个标签，不要复用旧账号已经打开、仍在运行的标签。
   - 一个新 Profile 只登一个账号；要再加账号，重新走一遍上面的步骤。

## 会清掉什么

「整套重新生成」与带站点数据重置的启动，清的是这个 Profile **所有站点**的数据，不只 Stripe：

- 所有站点的 Cookie，**包括 Link 登录状态**，重置后处处掉登录；
- localStorage、sessionStorage、IndexedDB、Service Worker、Cache Storage；
- HTTP 缓存、代码缓存、GPUCache，以及 `Default/Sessions` 里的会话记录。

保留：浏览器扩展本身及其 `chrome.storage`、书签、历史、偏好设置、Profile 配置、代理与 Passkey Box 配置。扩展若把数据写进网页的 localStorage，会和站点数据一起消失。

## 常见错误

| 错误 | 结果 |
| --- | --- |
| 只手动改种子，不重置 | 网站里的旧 Cookie、旧 `m` 和旧存储原样留着，等于旧设备换了一套指纹。要换身份走「整套重新生成」。 |
| 用「复制为新 Profile」代替新建 | 现在会换种子与设备标识；只是副本会继承旧资料目录里的站点数据，仍需确认重置。 |
| 多个 Profile 共用同一个出口 IP | 网络层先被关联，指纹再不同也只降一半关联度。每个新设备配独立出口。 |
| 首访用无头模式（`--headless`） | 屏幕固定为 800×600、DPR 1，窗口也不可信；先用有头模式完成首访。 |
| 在已有账号运行中的标签里登录另一个账号 | 页面还能写回旧存储，旧 `__stripe_mid` 和 Link 会话都还在。先重置，另开标签。 |
| 启动网址留空 | 没有预置身份，首报退化为 `NA`；虽然最终会拿到服务端值，但首访形态不干净。 |

## 当前局限

- **屏幕**：内核对屏幕开关不生效，屏幕与 DPR 由页面层脚本注入，`screen.availTop/availLeft` 按配置推导；窗口尺寸由启动参数决定，headless 下窗口与屏幕仍可能对不上。
- **字体**：没有可用的平台字体表，字体改写只是按种子增删本机 macOS 字体，真实 Windows/Linux 上的字体组合仍对不上。
- **Canvas 文本宽度**：内核的度量值有缺陷，目前靠页面层脚本修正，脚本本身仍可被高级探测看见。
- **引擎版本**：内置内核为 148，所有 Profile 共享同一个版本，不会随平台伪造更高版本。
- **宿主特征**：WebGPU 显卡、语音列表、本地字体枚举仍暴露这台 Mac；TLS、HTTP/2、`navigator.connection` 来自同一网络栈。
- **不等于免检**：新设备只是降低关联度，服务端黑盒仍可能加验；3DS 挑战率反而常见上升，这是正常的。

## 怎么自查

1. Profile 运行时执行一次自检，重点看这些项：
   - `platform`、`platform-version`、`brand`、`brand-version`；
   - `hardware`、`webgl`；
   - `languages`、`locale`、`date-string`、`time-zone`、`exit-time-zone`、`exit-language`；
   - `measure-text`、`canvas-stable`。
   能判断的项应为 `pass`。`info` 表示当前内核改不了或该项不适用，例如 Linux 的 WebGL、未配屏幕时的 `screen（跟随本机）`，单独记下即可。
2. 打开真实页面（Link 登录页或结账页），在开发者工具 Network 里过滤 `m.stripe.com`，检查 `/6` 报文：
   - 请求 Cookie 里应有 `__stripe_mid`：首报是 36 位小写 UUIDv4，服务端回 42 位后 Cookie 更新为 42 位，前 36 位不变；
   - 请求里还应有 `__stripe_sid`；
   - 响应体是 `{"muid","guid","sid"}`，首次响应会给 `.m.stripe.com` 下发 HttpOnly 的 `m`。
3. 30 分钟内再加载同一页面：
   - 请求仍带同一个 42 位 `__stripe_mid`；
   - 响应的 `guid` 与第一次相同。
   `guid` 每次加载都变，通常是三方 Cookie 没生效或 `m` 被清；`b.d`/`b.e` 为 `NA`，通常是启动网址缺失或种子写入失败。

注意：自检只读页面侧的事实，不访问 Stripe，也不写 Stripe 的 Cookie；身份相关的证据以第 2、3 步的真实报文为准。

## 最短清单

- [ ] 新建 Profile 或「整套重新生成」，已保存并完成清除；
- [ ] 启动网址就是登录域名；
- [ ] 独立代理，出口已检测，语言时区已跟随；
- [ ] 一致性提示无红项；
- [ ] 已关闭恢复上次会话；
- [ ] 有头模式、新标签、只登一个账号；
- [ ] 自检各项为 `pass`（`screen` 为 `info`），`guid` 跨加载稳定。
